# Heartfulness Remote — Wire & Security Protocol (v1, "HR1")

This document is normative. Server (`server/`), host agent (`agent/`), web
client (`web/`), Tauri client (`tauri/`) and Mac app (`mac/`) MUST follow it.
Shared Go implementation: `proto/`. Cross-language test vectors:
`testdata/vectors.json` (generated by `go run ./proto/cmd/genvectors`).

No custom cryptography: we only use Ed25519, SHA-256, HMAC-SHA256,
HKDF-SHA256 (RFC 5869), WebAuthn, and WebRTC DTLS-SRTP, all from platform
libraries (Go stdlib, WebCrypto, CryptoKit, ed25519-dalek, pion).

## 1. Goals

* All screen/audio/input/clipboard/file data flows **only** inside a WebRTC
  peer connection (DTLS-SRTP + SCTP-over-DTLS) between the Mac and an
  approved client device.
* The DTLS fingerprints in both SDPs are **signed by pinned Ed25519 device
  keys**, so the signaling server (or anyone controlling it, the DNS, or the
  TURN relay) cannot man-in-the-middle or impersonate either side.
* The **Mac is the root of trust**: it alone decides which device keys are
  trusted ("pinned"). The server only mirrors decisions it can verify via the
  Mac's signatures, and uses passkeys only to decide who may *talk to* it.

## 2. Identities and keys

| Key | Type | Where the private key lives |
|---|---|---|
| Host key `H` | Ed25519 | Mac Keychain (seed wrapped by a Secure Enclave key when available) |
| Device key `D` | Ed25519 | Browser: non-extractable WebCrypto key in IndexedDB. Tauri: OS keychain (macOS Keychain / Windows Credential Manager) |
| Owner passkey | WebAuthn | Phone/computer platform authenticator |
| Session token | 32 random bytes | Cookie `__Host-hr_session` (browser) or OS keychain (Tauri). Server stores only SHA-256 of it |

Public keys are raw 32-byte Ed25519 keys. **All binary values in JSON are
base64url without padding** ("b64"). Display fingerprint of a key:
lowercase RFC 4648 base32 (no padding) of `SHA-256(pub)[0:10]`, split in
groups of 4 with `-` (e.g. `abcd-efgh-ijkl-mnop`).

## 3. Signature transcript encoding ("TBS")

```
TBS(label, f1, f2, …, fn) = UTF8(label) || 0x00 || Σ ( u32be(len(fi)) || fi )
```

All fields are byte strings. Text is UTF-8. Integers (timestamps, unix
seconds) are their decimal ASCII representation. Keys/nonces/hashes are raw
bytes (decoded from b64 first). `H(x)` = SHA-256.

| Label | Signed by | Fields |
|---|---|---|
| `HR1/host-auth` | host | origin, serverNonce |
| `HR1/client-auth` | device | origin, serverNonce |
| `HR1/pair-challenge` | host | requestId, commit, na, hostPub |
| `HR1/pair-approve` | approving device | requestId, hostPub, devicePub, nd, na, name, kind |
| `HR1/cert` | host | hostPub, devicePub, name, kind, issuedAt |
| `HR1/revoked` | host | hostPub, devicePub, revokedAt |
| `HR1/revoke-request` | approved device | hostPub, targetPub, ts |
| `HR1/kill-request` | approved device | hostPub, action ("kill"\|"resume"), ts |
| `HR1/offer` | device | sessionId, hostPub, devicePub, clientNonce, hostNonce, H(offerSdp) |
| `HR1/answer` | host | sessionId, hostPub, devicePub, clientNonce, hostNonce, H(offerSdp), H(answerSdp) |

Non-signature derivations:

| Name | Definition |
|---|---|
| pair commit | `H(TBS("HR1/pair-commit", devicePub, nd))` |
| SAS | `u32be(H(TBS("HR1/sas", hostPub, devicePub, nd, na))[0:4]) mod 1_000_000`, zero-padded to 6 digits, displayed `123 456` |
| setup keys | `Kc = HKDF-SHA256(ikm=T, salt=∅, info="HR1/claim", L=32)`, `Ka = HKDF-SHA256(ikm=T, salt=∅, info="HR1/setup-auth", L=32)` |
| claim commit | `H(Kc)` |
| setup MAC | `HMAC-SHA256(Ka, TBS("HR1/setup", hostPub, devicePub, name, kind))` |

`origin` is the server's public origin string exactly as configured, e.g.
`https://heartfulness-remote.dedyn.io` (no trailing slash). Nonces are 32
random bytes; requestId and sessionId are 16 random bytes; `nd`/`na` are 32
random bytes. Timestamps in signed requests must be within ±300 s of the
verifier's clock.

## 4. Bootstrap ("claim") — first phone + passkey

1. Mac first run: creates `H`, connects to `wss://<domain>/ws/host` (§7), and,
   if the server reports `claimed:false`, generates a one-time setup secret
   `T` (32 bytes, memory only), sends `claimCommit = H(Kc)`, and shows a QR code
   for `https://<domain>/#setup=<b64 T>.<b64 hostPub>`.
2. Phone opens the URL. The web app reads the fragment, immediately removes it
   from the address bar (`history.replaceState`), and derives `Kc`, `Ka`.
   It pins `hostPub` from the QR code (authentic: it came from the Mac screen).
3. `POST /api/setup/begin {hostPub, claim: b64 Kc}` → server checks
   `H(Kc)` equals the claim commit of a connected pending host with that key →
   returns WebAuthn creation options.
4. Phone creates the passkey, generates its device key `D`, and calls
   `POST /api/setup/finish {flowId, credential, device:{pub, name, kind},
   setupMac: b64 HMAC(Ka, …)}`. Server creates the owner, binds the host,
   records the device as `pending`, sets the session cookie, and forwards
   `setup-device` to the host.
5. Host verifies `setupMac` with its `Ka` (the server only ever learned `Kc`,
   from which `Ka` cannot be derived) → pins `D`, issues a cert, forgets `T`.

A server that is not yet claimed accepts up to 5 concurrently-connected
pending hosts. If `HOST_PUBKEY` is set in the server environment, only that
host key is accepted. A malicious party racing the claim can only cause
denial of service (the real Mac then reports "server already claimed";
fix: `heartfulness-server reset` on the VPS).

## 5. Pairing a new device (approval with SAS + commitment)

Prevents the server from substituting keys. Commit-then-reveal makes SAS
grinding impossible (attacker success ≤ 10⁻⁶ per attempt, each attempt
visible to the owner).

```
Device D (new)          Server                 Host H           Approver (Mac UI or approved phone)
 pair-start{name,kind,commit} ─►
                         pair-request ───────► 
                         ◄────── pair-challenge{requestId, hostPub, na, sig_H}
 ◄── pair-challenge
 pair-reveal{devicePub, nd} ─►  ────────────► (host checks commit)
                         approval-needed ──────────────────────────────► (verifies sig_H with pinned hostPub,
                                                                          checks commit, shows name + SAS)
 shows SAS                                                       Mac dialog shows SAS
                         ◄──────────── pair-approve{approverPub, sig}  (or local approval on the Mac)
                         ◄────── pair-result{approved, cert}
 ◄── pair-approved{cert}  (device pins hostPub used in its SAS, verifies cert)
```

* The device MUST NOT reveal `devicePub, nd` before receiving `pair-challenge`.
* Host MUST generate `na` only after receiving the commit, and reject reveals
  that don't match the commit.
* Pending requests expire after 5 minutes; at most 3 pending at once; after 5
  denials in an hour the host auto-denies new requests for 1 hour.
* Approving device signs `HR1/pair-approve`; the host accepts it only if
  `approverPub` is pinned and not revoked.

## 6. HTTP API (`server/`)

All JSON. Cookie-authenticated, state-changing requests MUST carry header
`X-HR: 1` and an `Origin` equal to the configured origin (CSRF defence, plus
`SameSite=Strict`). Bearer tokens (`Authorization: Bearer <b64>`) are used by
the Tauri app; CORS is allowed only for the Tauri origins
(`tauri://localhost`, `http://tauri.localhost`, `https://tauri.localhost`),
without credentials.

| Method & path | Auth | Purpose |
|---|---|---|
| `GET /healthz` | – | `{"ok":true}` |
| `GET /api/status` | – | `{claimed, rpId, origin}` |
| `POST /api/setup/begin` | – | `{hostPub, claim}` → `{flowId, options}` |
| `POST /api/setup/finish` | – | `{flowId, credential, device:{pub,name,kind}, setupMac}` → cookie + `{ok}` |
| `POST /api/login/begin` | – | → `{flowId, options}` (discoverable credential, UV required) |
| `POST /api/login/finish` | – | `{flowId, credential}` → cookie + `{ok}` |
| `POST /api/logout` | session | revoke session |
| `GET /api/me` | session | `{host:{pub,name,online,state,sessionDeviceName}, devices:[{pub,name,kind,status,createdAt,lastSeen}], passkeys:[{id,name,createdAt}]}` |
| `POST /api/turn` | session | `{iceServers:[…], ttl}` (coturn REST credentials, 24 h) |
| `GET /api/nonce` | session | `{nonce}` single-use, 60 s, for "device proof" |
| `POST /api/passkeys/begin` | session + device proof | add another passkey |
| `POST /api/passkeys/finish` | session + device proof | |
| `POST /api/passkeys/delete` | session + device proof | `{id}` (never the last one) |
| `POST /api/link/start` | – | `{name}` → `{code:"ABCD-EFGH", pollToken, expiresIn:600}` |
| `POST /api/link/approve` | session | `{code}` (user types the code shown in the app) |
| `POST /api/link/poll` | – | `{pollToken}` → `{status:"pending"\|"approved"\|"expired", token?}` |

"device proof": body includes `devicePub`, `nonce` (from `GET /api/nonce`,
single-use, 60 s) and `sig` = `HR1/client-auth`(origin, nonce); device must be
`approved`.

Security headers on every response: strict CSP (`default-src 'none';
script-src 'self'; style-src 'self'; img-src 'self' data: blob:; media-src
'self' blob:; connect-src 'self'; font-src 'self'; manifest-src 'self';
worker-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors
'none'; require-trusted-types-for 'script'; trusted-types 'none'`), HSTS,
`X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, COOP
`same-origin`, CORP `same-origin`, `Permissions-Policy` (camera, microphone,
geolocation, payment, usb, serial, hid, midi, display-capture… disabled;
`fullscreen`, `clipboard-read`, `clipboard-write`, `keyboard-map`,
`screen-wake-lock`, `publickey-credentials-*`, `autoplay` = self; only feature
names current Chromium recognises, so the header logs no console errors).

Rate limiting (per client IP, behind the trusted reverse proxy): general
`/api/*` 5 req/s burst 20; auth endpoints (`setup/*`, `login/*`, `link/*`)
10/min; WebSocket upgrades 10/min. Lockout: 5 failed auth attempts
(WebAuthn failures, bad device/host signatures, bad link codes) from one IP
within 15 min → that IP is locked for 15 min (HTTP 429 + `Retry-After`).
More than 50 failures/hour server-wide → auth endpoints globally throttled to
1 request / 10 s for an hour.

## 7. WebSocket signaling

Text frames, one JSON object per frame, `type` field required, max 256 KiB.
Ping every 20 s; idle connections dropped after 60 s. Per-connection message
rate limit 50/s (burst 200).

### 7.1 `/ws/host` (the Mac)

```
S→H {type:"challenge", nonce}
H→S {type:"host-auth", hostPub, name, version, sig, claimCommit?}
S→H {type:"host-ready", claimed, origin, iceServers}    // or {type:"error", code}
H→S {type:"trust-sync", certs:[Cert], revocations:[Revocation]}
S→H {type:"turn", iceServers}                            // refreshed every 12 h
H→S {type:"host-status", state:"available"|"in-session"|"blocked", sessionDeviceName?}
```

`Cert = {hostPub, devicePub, name, kind, issuedAt, sig}` (§3 `HR1/cert`).
`Revocation = {hostPub, devicePub, revokedAt, sig}`. On `trust-sync` the server
marks exactly the certified devices `approved` (after verifying each sig),
the revoked ones `revoked`, and every other previously-approved device
`revoked` (the Mac is authoritative).

### 7.2 `/ws/client` (browsers, phones, Tauri)

```
C→S {type:"auth", token?}            // token only for bearer (Tauri); cookie otherwise
S→C {type:"challenge", nonce}
C→S {type:"device-auth", devicePub, sig}   // HR1/client-auth
S→C {type:"ready", device:{status:"unknown"|"pending"|"approved"|"revoked"},
                   host:{pub, name, online, state, sessionDeviceName}}
S→C {type:"host-status", online, state, sessionDeviceName}   // pushed on change
S→C {type:"devices-changed"}                                 // refetch /api/me
```

### 7.3 Routed messages (server relays; it fills `devicePub`/`requestId` from the authenticated connection, never trusts the client's claim)

Pairing (§5):

```
C→S   {type:"pair-start", name, kind, commit}
S→H   {type:"pair-request", requestId, devicePub:"" , name, kind, commit}
S→C   {type:"pair-pending", requestId}
H→S→C {type:"pair-challenge", requestId, hostPub, na, sig}
C→S   {type:"pair-reveal", requestId, devicePub, nd}
S→H   {type:"pair-reveal", requestId, devicePub, nd}
S→approved clients {type:"approval-needed", requestId, name, kind, devicePub, nd, commit, na, hostSig}
A→S→H {type:"pair-approve", requestId, approverPub, sig}
A→S→H {type:"pair-deny", requestId}
H→S   {type:"pair-result", requestId, approved:true, cert} | {…, approved:false, reason}
S→C   {type:"pair-approved", cert} | {type:"pair-denied", reason}
S→approved clients {type:"approval-closed", requestId}
S→H   {type:"setup-device", devicePub, name, kind, setupMac}   // bootstrap §4
H→S   {type:"device-approved", cert}                           // result of setup-device
```

Device management:

```
A→S→H {type:"revoke-request", targetPub, ts, approverPub, sig}
H→S   {type:"device-revoked", revocation}
A→S→H {type:"kill-request", action, ts, approverPub, sig}
```

Sessions:

```
C→S→H {type:"session-request", sessionId, devicePub, clientNonce, relayOnly?}
H→S→C {type:"session-accept", sessionId, hostNonce}
H→S→C {type:"session-reject", sessionId, reason}  // "blocked"|"busy"|"not-trusted"|"browser-disabled"|"error"
C→S→H {type:"offer", sessionId, sdp, sig}
H→S→C {type:"answer", sessionId, sdp, sig}
C↔S↔H {type:"ice", sessionId, candidate}          // RTCIceCandidateInit JSON, or null = end
C↔S↔H {type:"session-end", sessionId, reason}
```

The host MUST verify the offer signature against the **pinned** device key
(never a key supplied by the server), check sessionId/nonces match the
accepted request and are unused, and the offer must arrive within 60 s. The
client MUST verify the answer signature against its **pinned** host key
before `setRemoteDescription`. Both sides MUST reject SDPs that contain no
`a=fingerprint:sha-256` line or contain more than one distinct fingerprint.
ICE candidates are not signed (they cannot affect DTLS authentication).

## 8. Data channels (created by the client in its offer)

| Label | Options | Content |
|---|---|---|
| `control` | ordered, reliable | JSON text |
| `input` | ordered, reliable | JSON text (keys, buttons, wheel, text) |
| `pointer` | `ordered:false, maxRetransmits:0` | JSON text (pointer moves) |
| `file` | ordered, reliable | binary: 16-byte transfer id ‖ chunk (≤ 16 KiB) |

Media: host sends one video track (H.264, or H.265 when both sides support
it) and one Opus audio track (48 kHz stereo). Client offers `recvonly`
transceivers for both.

### 8.1 Control messages (`t` field)

```
H→C {t:"hello", hostName, version, displays:[{id,name,width,height,scale,primary}],
     activeDisplay, codec, features:{audio,clipboard,files}}
C→H {t:"select-display", id}
C→H {t:"quality", mode:"auto"|"sharp"|"smooth", maxKbps?}
C→H {t:"keyframe"}
C↔H {t:"ping", id, ts} / {t:"pong", id, ts}
C↔H {t:"clip", text}                         // ≤ 1 MiB
C→H {t:"ls", reqId, path}                    // path relative to the Mac user's home; "" = home
H→C {t:"ls-result", reqId, path, entries:[{name,dir,size,mtime}], error?}
C→H {t:"get", reqId, path}                   // download a file from the Mac
H→C {t:"file-start", id, name, size, dir:"down", reqId}
C→H {t:"file-start", id, name, size, dir:"up"}
H→C {t:"file-accept", id} | {t:"file-reject", id, reason}
C↔H {t:"file-end", id, sha256}
H→C {t:"file-saved", id, name} | {t:"file-error", id, reason}
C↔H {t:"file-cancel", id}
H→C {t:"notice", level:"info"|"warn", text}
H→C {t:"bye", reason}
```

Uploads are saved to `~/Downloads/Heartfulness Remote/` with a sanitized
file name (no path separators, no leading dots, de-duplicated). Downloads are
restricted to the Mac user's home folder; symlinks escaping it are refused.
SHA-256 is verified on both directions.

### 8.2 Input messages

```
pointer: {t:"m", x, y}                       // 0..1 within the active display
input:   {t:"b", b, d, x, y}                 // b = DOM button (0 left,1 middle,2 right,3 back,4 fwd), d = down?
         {t:"w", dx, dy, x, y}               // wheel in CSS pixels, DOM sign convention
         {t:"k", c, d}                       // c = KeyboardEvent.code, d = down?
         {t:"txt", s}                        // unicode text (≤ 4096 chars)
         {t:"reset"}                         // release all keys and buttons
```

## 9. Host agent ⇄ Mac app IPC (`agent/` ⇄ `mac/`)

The Swift app launches the bundled `hr-agent` helper and talks to it over
**stdin/stdout pipes** (no sockets). Frame = `u32be(len) ‖ u8 type ‖ payload`,
where `len` counts type + payload, max 16 MiB. Diagnostics go to stderr
(never secrets).

Swift → agent:

| Type | Name | Payload |
|---|---|---|
| 0x01 | CONFIG | JSON `{serverURL, hostPub, hostName, dataDir, storageKey, settings:{allowBrowserClients, relayOnly, idleTimeoutMin, maxKbps, codec:"auto"\|"h264"\|"h265"}, hevcAvailable, audioAvailable}` (storageKey = b64 32 bytes from Keychain, used for HMAC of local files) |
| 0x02 | SIGN_RESULT | JSON `{id, sig}` |
| 0x03 | VIDEO | `u8 codec (1=H264, 2=H265) ‖ u8 flags (bit0 keyframe) ‖ u64be pts_us ‖ Annex-B access unit` |
| 0x04 | AUDIO | `u64be pts_us ‖ Opus packet (20 ms)` |
| 0x05 | COMMAND | JSON `{cmd, …}`: `kill`, `resume`, `disconnect`, `approve{requestId}`, `deny{requestId}`, `revoke{devicePub}`, `settings{…}`, `clipboard{text}`, `displays{list, active}`, `log-read{limit}`, `new-setup-code`, `quit` |

Agent → Swift:

| Type | Name | Payload |
|---|---|---|
| 0x81 | SIGN_REQUEST | JSON `{id, data}` (data = b64 TBS bytes; Swift signs with `H`) |
| 0x82 | STATE | JSON `{server:"offline"\|"connecting"\|"online"\|"error", serverError?, claimed, setupURL?, killed, session:null\|{device:{pub,name,kind}, since, transport:"direct"\|"relay", rttMs}, pending:[{requestId,name,kind,sas,expiresAt}], devices:[{pub,name,kind,addedAt,lastUsed}]}` |
| 0x83 | INPUT | JSON input message (§8.2) plus `display` id |
| 0x84 | ENCODER | JSON `{cmd:"start", codec, fps, kbps, display}` \| `{cmd:"stop"}` \| `{cmd:"keyframe"}` \| `{cmd:"bitrate", kbps}` \| `{cmd:"display", id}` |
| 0x85 | AUDIO_CTL | JSON `{cmd:"start"\|"stop"}` |
| 0x86 | CLIPBOARD_SET | JSON `{text}` |
| 0x87 | EVENT | JSON `{event, device?, detail?}` — `session-start`, `session-end`, `pair-request`, `device-added`, `device-removed`, `killed`, `resumed`, `idle-warning`, `file-received` (Swift shows notifications/banner) |
| 0x88 | LOG | JSON `{entries:[…], verified:bool, error?}` |

The agent owns `pins.json` (trusted devices) and `access-log.jsonl` in
`dataDir`. Both are integrity-protected with `HMAC-SHA256(storageKey, …)`;
the access log is a hash chain (`entry.prev = H(previous line)`, plus
`mac = HMAC(storageKey, line-without-mac)`), so edits, deletions and
re-ordering are detected.

### 9.1 Implementation notes (the Go agent is authoritative where this section and the tables above differ)

* `STATE`: device and session-device objects also carry `fingerprint`; `session`
  carries `codec`; timestamps are unix **seconds** and `0` means "never";
  `pending[].sas` is pre-formatted (`"196 924"`); `rttMs` is an integer;
  `setupURL` is present only while the server is online **and** unclaimed.
* `EVENT.detail` is always a string. Additional events: `trust-store-*`,
  `log-tampered`, `setup-failed`.
* `ENCODER.start.profile` is `"high"`, `"main"` or `"baseline"` (H.264) and the
  `bitrate` command may also carry a new `fps`.
* `SIGN_REQUEST.id` is a number, starting at 1 for each helper process; frames
  from a previous helper instance must be ignored.
* `COMMAND` also supports `reset-trust-store` (forget all pinned devices after a
  tamper alarm; devices must pair again).
* `settings.maxKbps` is clamped to 1 000–250 000; plain `http://` server URLs
  are accepted only for `localhost` and loopback IPs.
* Access-log entries: `{seq, ts, event, device?, deviceFp?, transport?,
  durationSec?, file?, size?, detail?, prev, mac}`; their event names
  (`session-start`, `session-end`, `pairing-approved`, `device-added`,
  `log-tamper-detected`, …) are distinct from `EVENT` names.
* Data channel: a failed `get` is reported as `file-error` with `reqId` (and no
  `id`, because no transfer started). `bye` / `session-end` reasons include
  `host-shutdown`, `host-disconnected`, `offer-rejected`, `no-common-codec`,
  `connect-timeout`, `offer-timeout`, `connection-failed`, `connection-closed`,
  `trust-reset`, `browser-disabled`, `idle-timeout`, `killed`, `revoked`, `user`.
* `/ws/client` `ready.device` also carries `cert` when approved.

## 10. Multiple Macs (HR1.1) — normative, supersedes the single-host parts of §4–§7

One owner account can hold **up to 20 Macs** ("hosts"). Each Mac remains its
own root of trust: a device must be approved **on each Mac** it wants to
control (§5, unchanged crypto, now routed by `hostPub`).

### 10.1 Mac ID

`macId = u32be(H(TBS("HR1/mac-id", hostPub))[0:4]) mod 10^9`, zero-padded to 9
digits, displayed `482 913 557`. It is a **display/lookup** convenience only —
never trusted for authentication. Clients compute it themselves from the
pinned `hostPub`.

### 10.2 Adding another Mac ("join")

A Mac that connects to a **claimed** server with a host key the server does not
know becomes a *pending join host* (kept while connected, max 5, 30 min). The
server answers `host-ready {claimed:true, joined:false, …}`.

1. The Mac generates a join secret `T` of **10 random bytes** (80 bits, memory
   only), derives `Kc`, `Ka` exactly as in §3 (HKDF of `T`), sends
   `claimCommit = H(Kc)` in `host-auth`, and shows:
   * QR: `https://<domain>/#join=<b64 T>.<b64 hostPub>`
   * typed form: **Mac ID** + **join code** = RFC 4648 base32 of `T`
     (16 chars, shown `K7QP-3MZD-WX2R-9TFA`). Clients normalise input:
     uppercase, drop spaces/dashes, map `0→O`, `1→I`, `8→B`.
2. An **approved device** of the owner (any device approved on at least one
   Mac), signed in with a passkey:
   * typed path only: `GET /api/hosts/pending?macId=…` → `{hostPub, name}`;
     the client checks `macId(hostPub)` equals what was typed;
   * `POST /api/hosts/join/begin {hostPub, claim:b64 Kc, …device proof}` →
     server checks `H(Kc)` against that pending host's commit → `{flowId, name, macId}`;
   * `POST /api/hosts/join/finish {flowId, setupMac, …device proof}` where
     `setupMac = HMAC(Ka, TBS("HR1/setup", hostPub, devicePub, name, kind))`
     (name/kind = this device's registered name/kind).
3. Server → that host: `setup-device {devicePub, name, kind, setupMac}` (same as §4).
4. Host verifies `setupMac` with `Ka`, pins the device, issues a cert and
   answers `device-approved {cert, hostMac}` with
   `hostMac = HMAC-SHA256(Ka, TBS("HR1/join-confirm", hostPub, devicePub))`,
   then forgets `T`. (§4 claims also send `hostMac` now.)
5. Server verifies the cert against that host key, **binds the host to the
   owner** (only now), and sends the device
   `host-joined {hostPub, cert, hostMac}` + broadcasts `hosts-changed`.
6. The device verifies the cert **and** `hostMac` (with its `Ka`) before
   pinning `hostPub`. `hostMac` proves the key belongs to the Mac that showed
   the code; the server, which never learns `T` or `Ka`, cannot forge it
   (80-bit secret, single use, short-lived).

`POST /api/hosts/remove {hostPub, …device proof}` unbinds a Mac (its socket is
closed with `error {code:"removed"}`; the Mac shows a new join code).
`HR_HOST_PUBKEY` (optional) becomes a comma-separated allow-list.

### 10.3 Routing

Client→server messages that target a Mac carry `hostPub`: `pair-start`,
`pair-approve`, `pair-deny`, `session-request`, `revoke-request`,
`kill-request`. Server→client messages that come from a Mac carry its
`hostPub`: `pair-challenge`, `pair-approved`, `pair-denied`,
`approval-needed`, `approval-closed`, `session-accept`, `session-reject`,
`answer`, `ice`, `session-end`, `host-status`, `host-joined`. `offer`, `ice`
and `session-end` from the client carry `sessionId` (the server maps it to
the Mac) and also `hostPub`.

`approval-needed` is sent only to devices approved **on that Mac**; a
`pair-approve` is verified by that Mac against its own pins. `trust-sync`,
certs and revocations from a Mac only change device approvals **for that
Mac**.
